# 00. 園開設コマンド・スタッフ権限設計

## 対象

- 運営者による園登録
- 初回 owner スタッフ作成
- `kindergarten_staff.role` ごとの権限整理

## 目的

- 初期フェーズでは公開の園登録画面を持たず、運営者が Laravel command から園を開設する。
- 園作成と初回スタッフ作成を同一トランザクションで行い、テナントと認証情報の不整合を防ぐ。
- 園側の認可設計で必要となる `owner` / `staff` の権限差分を先に明文化する。

## 1) 園開設の基本方針

- 園登録は Laravel Artisan command で実行する。
- 公開フォームやセルフサーブ登録は初期段階では導入しない。
- Excel で園情報を受け取ること自体は許容するが、登録は必ず command もしくは同じ Application Service を通す。
- DB 直接更新は運用として採用しない。

## 2) 想定コマンド

**Command**: `php artisan kindergarten:create`

### 引数・オプション案

| フィールド | 形式 | 必須 | バリデーション | 説明 |
|---|---|---|---|---|
| `name` | option | 必須 | max:120 | 園名 |
| `owner-name` | option | 必須 | max:100 | 初回 owner スタッフ氏名 |
| `owner-email` | option | 必須 | email, max:255, `kindergarten_staff.email` で一意 | 初回 owner スタッフメール |
| `send-invite` | flag | 任意 | boolean | 初回設定メール送信フラグ |

### 実行例

```bash
docker compose exec php php artisan kindergarten:create \
  --name="サンプル保育園" \
  --owner-name="山田 太郎" \
  --owner-email="owner@example.com" \
  --send-invite
```

## 3) コマンドの処理フロー

1. 入力値を検証する。
2. `kindergartens` に園を作成する。
3. `kindergarten_staff` に `role=owner` の初回スタッフを作成する。
4. 初回ログイン用のセットアップ状態を作成する。
5. `--send-invite` 指定時は初回パスワード設定案内を送信する。
6. 園と owner 作成結果を標準出力に表示する。

## 4) トランザクション要件

- `kindergartens` 作成と `kindergarten_staff` 作成は同一トランザクションで実行する。
- owner スタッフ作成に失敗した場合は園作成もロールバックする。
- メール送信はDBコミット後に非同期キューまたは後続処理で行う。

## 5) 初回認証の設計方針

- owner スタッフを平文パスワード付きで発行しない。
- 初回ログインは「パスワード設定トークン」または「スタッフ招待トークン」経由で行う。
- トークンは平文保存せず、ハッシュ化して保存する。
- トークン有効期限切れ時は運営者が再発行する。

## 6) 実装責務の分離

### Command

- CLI引数の受け取り
- 入力エラー表示
- Application Service 呼び出し
- 実行結果の出力

### Application Service

- 園作成
- owner スタッフ作成
- 初回設定トークン発行
- トランザクション制御

### Notification / Mail

- 初回パスワード設定案内送信
- 再発行案内送信

## 7) `kindergarten_staff.role` の定義

| role | 説明 |
|---|---|
| `owner` | 園の初回責任者。設定系・スタッフ管理系を含む全操作を行える |
| `staff` | 通常スタッフ。日常運用に必要な操作のみ行える |

## 8) 権限マトリクス

| 操作 | owner | staff |
|---|---|---|
| 自分のログイン/ログアウト | 可 | 可 |
| 自園データの参照 | 可 | 可 |
| 園児登録・編集・在籍管理 | 可 | 可 |
| 保護者招待QR発行 | 可 | 可 |
| 招待失効・再発行 | 可 | 可 |
| 紐づけ済み保護者一覧確認 | 可 | 可 |
| 紐づけ解除 | 可 | 可 |
| 紐づけ復元 | 可 | 可 |
| アルバム作成 | 可 | 可 |
| 写真アップロード | 可 | 可 |
| 写真タグ付け・価格設定 | 可 | 可 |
| Stripe Connect 開始/再連携 | 可 | 不可 |
| 園の基本情報編集 | 可 | 不可 |
| staff 招待・追加 | 可 | 不可 |
| staff 権限変更 | 可 | 不可 |
| staff 停止/削除 | 可 | 不可 |

## 9) 認可ルールの補足

- `owner` / `staff` の差分は `Policy` または `Gate` に集約する。
- Controller やフロントエンドで都度 `role` 分岐を複製しない。
- `staff` は自園データの運用系操作を担当し、テナント設定変更やスタッフ管理は `owner` に限定する。
- 将来的に権限粒度が不足した場合でも、まずは `owner` / `staff` の2段階を維持し、必要性が明確になってから権限追加を検討する。

## 10) 将来の拡張

- CSV一括登録が必要になった場合も、内部では本コマンドと同じ Application Service を利用する。
- 将来、運営者向け管理画面を作る場合も同一の作成ロジックを再利用する。
- 監査ログが必要になった場合は、園作成者、作成日時、staff追加・停止履歴を記録する。
