# 未確定事項・今後の検討課題

設計を進める中で意図的に先送りにした、または今後ユーザー（開発者）自身の
判断が必要な項目を列挙する。

## 1. プロダクト仕様

- **価格設定**: 写真1枚ごとの単価固定か、まとめ買い割引・アルバム単位販売を
  用意するか
- **返金・キャンセルポリシー**: 購入後の返金は許容するか、許容する場合
  `entitlements` の失効タイミングをどう扱うか
- **写真・データの保存期間**: 卒園後何年間、写真とアカウントデータを
  保持するか（ストレージコストと、個人情報の保存期間最小化の両立）
- **通知**: 新しい写真が公開された際のメール/プッシュ通知は必要か
- **園児名の表示範囲**: 招待画面や購入画面に園児の氏名をどこまで表示するか
  （フルネーム表示は誤操作防止に有効な一方、URL経由での情報露出は最小化したい）

## 2. 認証・アカウント関連

- **メール確認の必須化タイミング**: アカウント作成直後に必須にするか、
  購入時のみ必須にするか（04章末尾で言及した段階的制限の採否）
- **同一メールアドレスの重複登録**: 保護者が離婚等で連絡先を分けたい場合など、
  1園児に3人以上の保護者を紐づける必要が生じた場合の運用（QR発行枚数を
  可変にするだけで対応可能な設計にはなっている）

## 3. 将来拡張候補（MVPには含めない）

- **顔認識による自動タグ付け**: 手動タグ付けの負荷が高くなった場合の
  自動化。精度検証とプライバシー影響評価が別途必要
- **複数園（法人・複数拠点）対応**: 1つの運営法人が複数の園を持つ場合に
  スタッフアカウントが園をまたいで操作できるようにするか
- **保護者アプリのプッシュ通知（PWA/ネイティブ）**

## 4. インフラ

- **ECS Fargateのパブリックサブネット直接配置の可否**: NAT Gatewayの固定費
  （$45/月〜）を回避するため、Fargateタスクをパブリックサブネットに置き
  パブリックIPを付与する構成を想定しているが、セキュリティグループ設計を
  慎重に行う必要がある（詳細は[05_tech_stack.md 4.2](./05_tech_stack.md#42-コストを抑えるための構成方針)）
- **Fargate Spotの採用可否**: compute費用を最大70%削減できるが、
  2分前通知でのタスク中断リスクがあるため、常時起動と割引のどちらを
  優先するか未確定

## 5. 非機能・運用

- **Nuxt4のレンダリング方式**: 保護者・スタッフ向け画面はログイン必須のため
  SEOの恩恵が薄く、基本はSPAモードで問題ないと想定している。ただし園向けの
  紹介LP（営業用）を同一プロジェクトで持つ場合はそのページのみSSR/SSGにする
  ハイブリッド構成を検討する
- **決済まわりの税務・法務**: インボイス対応、特定商取引法に基づく表記など、
  個人開発でもサービス公開する場合は別途整理が必要（本ドキュメントの
  スコープ外）。なお入金先をStripe Connectで園ごとに分離したことで資金移動業
  該当リスクは軽減しているが、手数料に対する消費税処理など税務面の整理は
  別途必要
- **Stripe Connectの手数料率・負担者**: プラットフォーム手数料（`platform_fee_amount`）
  の料率、および決済手数料（Stripe側の取り分）を運営者・園のどちらが実質的に
  負担する設計にするかは未確定。
  下記を想定。
  アカウントタイプ：Express
  支払いタイプ：デスティネーション支払い
- **監視・ログ**: 認可まわり（誰がどの写真にアクセスしたか）は
  監査ログとして残す設計にすると、個人情報を扱うSaaSとしての信頼性を
  ポートフォリオ上もアピールしやすい
